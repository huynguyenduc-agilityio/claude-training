# EXP-110: An invalid pricing.json is accepted silently and gives wrong costs

- **Type:** Bug
- **Priority:** Medium
- **Reporter:** Claude review of EXP-107 (PR #4, point 5)

## Description

`loadPricing` trusts `app/server/data/pricing.json` and checks nothing. A typing mistake in that file
does not stop the server. It shows up later as a wrong number, or as a crash far from the cause:

- A `from` that cannot be parsed makes `Date.parse` return `NaN`. `findPrice` then never picks that
  period, so the older price keeps being used and nothing reports it.
- A negative price gives a negative cost.
- A missing or non-numeric price gives a `NaN` cost.
- A model with an empty list of periods is a known model with no price.
- A model whose value is not a list throws `periods.toSorted is not a function`, which does not say
  which model is wrong.

## Acceptance criteria

- `loadPricing` throws when the table is invalid, and the message names the model, the period number
  and the reason.
- Invalid means any of these:
  - the file's top level is not an object
  - the table has no models
  - a model's value is not a non-empty list
  - a period is not an object
  - `inputPerMTok`, `outputPerMTok` or `cachedInputPerMTok` is missing, not a finite number, or
    negative
  - `from` is present but is not a real ISO 8601 UTC instant, such as `2026-10-01T00:00:00Z`; a day
    that does not exist, such as `2026-02-30`, is invalid, and so is the hour `24`
- A price of `0` is valid.
- A period without `from` is valid, and so is a model whose periods all have `from`.
- The current `pricing.json` loads unchanged, and all existing tests pass unchanged.
- The API does not start with an invalid file: the process exits and prints the message.
- `findPrice`, `getPrice` and the API responses do not change.

## Repro (filled in by the developer)

Reproduced on `main` at `39dc3ac` with the new tests of `pricing.test.ts`, run before any change to
`pricing.ts`: 49 tests, 29 failed, 20 passed. Each case wrote a temporary `pricing.json` and called
`loadPricing`. Nothing validates the file, so the actual result depends on what the file holds:

| Content of the file | Expected | Actual |
|---|---|---|
| top level is an array (`[]`) | throws, names the problem | no error, an empty table is returned |
| top level is `null` | throws, names the problem | throws `Cannot convert undefined or null to object` |
| a model's value is an object, a string or a number | throws, names the model | throws `periods.toSorted is not a function`, no model named |
| a model's value is `null` | throws, names the model | throws `Cannot read properties of null (reading 'toSorted')` |
| a model with an empty list `[]` | throws, names the model | no error, a known model with no price |
| a period is a string, an array or a number | throws, names model and period | no error |
| a period is `null` | throws, names model and period | throws `Cannot read properties of null (reading 'from')`, no model named |
| a price field missing, a string, `null` or negative (3 fields, 4 cases) | throws, names model, period and field | no error, the wrong value is kept |
| `from` is `not-a-date`, `Oct 1 2026`, `2026-10-01T00:00:00`, `2026-10-01` or a number | throws, names model and period | no error |
| two bad entries in one file | throws at the first | no error |

- Not failing before the change, as expected: a price of `0`, a period without `from`, a model whose
  periods all have `from` (one with milliseconds), extra fields in a period, and the real
  `pricing.json`. They guard against the check being too strict.
- No test needed a change: `git diff` of the test file shows only added lines.
- The ticket's example `periods.toSorted is not a function` is real, but only for a model whose value
  is a string, an object or a number. Even then, the message does not say which model is wrong.
- Found by `/code-review` after the first fix: `Date.parse` rolled `2026-02-30T00:00:00Z` over to
  `2026-03-02T00:00:00.000Z`, and `{}` loaded with no models. Both are now rejected, with tests.
- Found by Claude's review of EXP-107 (PR #4, point 5).
