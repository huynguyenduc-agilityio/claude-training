# EXP-107: Model names like "constructor" are accepted and break the month

- **Type:** Bug
- **Priority:** High
- **Reporter:** QA (Day 6 test coverage audit)

## Description

`POST /api/usage` should reject a model that is not in the price table, but some names pass the
check: `constructor`, `toString`, `__proto__` and the other names every JavaScript object has. The
record is saved, and from then on every request that reads the usage records fails with `500`
until someone deletes the row from the database.

Steps:

1. Send:
   ```json
   {
     "timestamp": "2026-10-15T03:00:00Z",
     "model": "constructor",
     "project": "support-bot",
     "inputTokens": 10,
     "outputTokens": 1
   }
   ```
2. The API answers `500`, but the record is saved.
3. Open the dashboard for any month, or post another valid record: both fail with `500`.

## Acceptance criteria

- A model that is not a key of the price table itself (including `constructor`, `toString`,
  `hasOwnProperty`, `__proto__`) is rejected with `400` and `Unknown model: <name>`; nothing is
  saved.
- Looking up a price for such a name fails with the same `Unknown model` error.
- Every model in `app/server/data/pricing.json` is still accepted.

## Repro (filled in by the developer)

Reproduced on `main` at `4ab78dc` with an in-memory database and the real app:

| Request | `model: "constructor"` | `model: "__proto__"` |
|---|---|---|
| `POST /api/usage` | 500 (record saved) | 500 (record saved) |
| `GET /api/usage?month=2026-10` | 500 | 500 |
| `GET /api/summary?month=2026-10` | 500 | 500 |
| `POST /api/usage` with a valid record | 500 | 500 |

- Error: `TypeError: periods.findLast is not a function` in `getPrice` (`pricing.ts:36-39`):
  `table[model]` returns a function or an object instead of the list of price periods.
- Cause: `if (!pricing[model])` (`usage.validation.ts:41`) is truthy for names inherited from
  `Object.prototype`. On the audited commit `c0257f9` the `POST` answered `201`; since EXP-102 the
  budget alert prices the new record during the `POST`, so it answers `500` after saving it.
- Found by the cloud coverage audit (`docs/lessons/day-06-flagship-parallel/cloud-coverage-audit.md`, H2).
