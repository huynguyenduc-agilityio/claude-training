# EXP-115: Fix project budget edge cases found in the Day 14 review

- **Type:** Bug
- **Priority:** Low
- **Reporter:** Day 14 review: `/code-review high` and ultrareview on the review-only GitHub PR #8,
  findings confirmed by the owner on 2026-11-16
- **Spec:** [project-budgets/spec.md](../capstone/project-budgets/spec.md), R1, R8, R11 to R13 and the
  API contract
- **Depends on:** EXP-112, EXP-113, EXP-114 (all merged)

## Description

As the budget owner, I want project budgets to work the same for every project name and every amount
the app accepts, so that no project shows in the wrong order or cannot be saved.

The review of the merged capstone found four defects. Each needs an unusual project name or a very
large amount, so none shows with the sample data:

- **A.** `GET /api/project-budgets` sorts projects by UTF-16 code unit, not by code point as the spec
  says. The web already compares code points, so the form's order and the banners' tie-break disagree.
- **B.** A project named `.` or `..` cannot get a budget. The browser shortens
  `/api/project-budgets/..` to `/api/` before sending it, so Save and Remove answer 404. Encoding the
  dots as `%2E` does not help: the URL parser treats `%2E%2E` as `..` too. Decision of the client
  (2026-11-16): such names are not accepted as project names.
- **C.** On the form, a project named after an `Object.prototype` property (`constructor`,
  `toString`, `__proto__`) keeps its row state in a plain object, so the lookup returns the inherited
  property. Save then shows neither "Saved" nor the error message.
- **D.** The banner order compares shares by multiplying whole cents (`s1 × b2` against `s2 × b1`).
  Above `2^53` the products lose precision, so two different shares can compare as equal and fall back
  to name order.

## Acceptance criteria

```gherkin
Feature: Project budgets work for every accepted name and amount

  Scenario: 1. The API lists projects in code-point order
    Given usage records exist for the projects "proj-～" (U+FF5E) and "proj-😀" (U+1F600)
    When I call GET /api/project-budgets
    Then "proj-～" comes before "proj-😀" in "projects"

  Scenario Outline: 2. A usage record cannot use "." or ".." as its project
    When I call POST /api/usage with a valid record whose project is "<project>"
    Then the response is 400 with {"error": "project must not be \".\" or \"..\""}
    And no record is stored

    Examples:
      | project |
      | .       |
      | ..      |

  Scenario Outline: 3. Names with dots that are not only dots stay valid
    When I call POST /api/usage with a valid record whose project is "<project>"
    Then the response is 201

    Examples:
      | project |
      | ...     |
      | .hidden |
      | a.b     |

  Scenario Outline: 4. The form works for a project named after an Object property
    Given usage records exist for the project "<project>"
    When I enter 10 as its budget and press Save
    Then its row shows "Saved" and "$10.00"
    When I enter 10.005 and press Save
    Then its row shows "budgetUsd must have at most 2 decimals"

    Examples:
      | project     |
      | constructor |
      | toString    |
      | __proto__   |

  Scenario: 5. Banner order is exact for large amounts
    Given project "a" has spent $2,999,999.96 of a $999,999.99 budget this month
    And project "b" has spent $2,999,999.99 of a $1,000,000.00 budget this month
    When the dashboard shows the banners
    Then the banner for "b" comes before the banner for "a"
```

More rules:

- Scenario 5 shares, in whole cents: `a` is 299999996 / 99999999 and `b` is 299999999 / 100000000.
  `299999999 × 99999999 − 299999996 × 100000000 = 1`, so `b` is higher; in JavaScript numbers both
  products round to the same value and the difference is `0`.
- The error text in scenario 2 is checked after `project is required`, so an empty project still gives
  `project is required`.
- Records stored before this change are not migrated. A project already named `.` or `..` still cannot
  get a budget; that is accepted.
- No other response, text or order changes.

## Scope

- Server: code-point sort in the project budget list; the `.` and `..` check in the usage validation.
- Web: row state of the "Project budgets" form keyed so that no project name can hit an inherited
  property; exact share comparison in the banner order.
- Tests for each scenario; `spec.md` updated for the new usage rule and the exact comparison.

## Non-scope

  default repository in `createApp` (by design, EXP-112 plan), the double `listAll()` per PUT, the
  hard-coded 80% threshold, and code simplifications.
